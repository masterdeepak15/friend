# Friend Phase 1 "Core" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a secure self-hosted gateway, tool-using agent, CLI device node and a minimal agent-controlled full-screen web stage with a particle-sphere presence.

**Architecture:** A Node/TypeScript gateway (Fastify + `ws` + SQLite) authenticates the owner, runs an agent loop against a provider interface (Claude first), routes tool calls through a policy engine to a device node, and streams stage commands and captions to a React/Three.js client. Approvals and PIN entry are drawn only by the client. All messages are zod schemas in a shared `protocol` package.

**Tech Stack:** Node 20+, TypeScript (ESM), pnpm workspaces, Fastify, `ws`, `better-sqlite3`, `zod`, `@anthropic-ai/sdk`, React, Vite, Three.js, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-07-friend-core-design.md`

## Global Constraints

- Node 20+, ESM, pnpm monorepo; packages `protocol`, `server`, `agent-cli`, `web` under `packages/`.
- Data directory `~/.friend` (config, SQLite database, logs). Tests use a temp directory, never the real one.
- Password and PIN hashed with Node built-in `crypto.scrypt` and per-user salt; comparisons constant-time. PIN is numeric, minimum 6 digits.
- Gateway binds `127.0.0.1` by default. Config keys: `bind`, `publicUrl`, `trustProxy`, `allowedOrigins`. Authentication is on in every mode.
- Web session cookie is `HttpOnly`, `SameSite=Strict`, and `Secure` automatically over HTTPS. Device tokens are random and stored hashed. Pairing codes expire after 5 minutes.
- Agent loop step limit 20. `shell.run` timeout 60 s with output size cap. Approval timeout 120 s means deny.
- Risk tiers T0 read, T1 write in allowed roots, T2 act, T3 critical. T3 always requires the PIN and can never be auto-allowed by a rule. Guest trust denies everything except stage presence/caption.
- Approval card text is generated by the server from the real tool arguments, never from model-written text. The agent cannot create, dismiss or answer approvals.
- The client renders agent UI only from its trusted catalog; Markdown is sanitized; no raw HTML or script from the agent.
- Presence: Three.js `Points` on a Fibonacci sphere, 6k–12k points scaled by device, states `idle|listening|thinking|speaking`, API `setState(state)` and `setAmplitude(0..1)`, 2D canvas fallback, `prefers-reduced-motion` support. Touch targets at least 44 px.
- Secrets never appear in logs or audit detail.
- Every commit message ends with the trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A tool result, file, or model text that says "approved" or "the owner agreed" must not approve anything; only a client `approval.respond` can. (Task 10, Task 12)
2. File paths using `..`, symlinks, mixed `\` and `/`, different drive letters or letter case must not escape the allowed roots on Windows. (Task 7)
3. Huge or binary output from `fs.read` and `shell.run` must be truncated and flagged, never crash the gateway or flood the client. (Task 7)
4. Browser reconnect during a turn or pending approval, and two tabs open at once: state resyncs, an approval is shown once and answered once. (Task 13)
5. A second `chat.send` while a turn is running is rejected with a clear status rather than interleaving. (Task 12)
6. Malformed JSON, unknown message types and oversized WebSocket frames close or reject cleanly without crashing the server. (Task 5)
